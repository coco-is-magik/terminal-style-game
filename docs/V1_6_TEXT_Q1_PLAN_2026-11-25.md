# V1-6 Unicode UI, Editing, Clipboard, and IME — Q1 Plan — 2026-11-25

## Provenance and status

**Delivered.** All eight increments have landed: I0 (`grid_print` reads UTF-8), I1 (`text_edit`), I2
(the chrome's face and UI missing-glyph diagnostics), I3 (authored content becomes validated UTF-8),
I4 (the editor's fields gain a cluster-safe caret and selection), I5 (clipboard paste under D-E) and I6
(IME composition through SDL's text-input path), and I7, which makes every refusal I3–I5 produced
visible in the editor instead of only to its caller. What remains is the native acceptance this
environment cannot run, listed per increment and again at the end. Decisions D-A–D-G stand as written except D-C, which was taken as recommended: RTL is
refused with a typed diagnostic rather than implemented in this phase. Each increment's record is under
[Progress](#progress) at the end.

V1-6's prerequisites are met: V1-3's pointer model is delivered and V1-5 closed its required outcomes
today, including the `utf8proc` vendoring (I6) that this phase is the first consumer of. The roadmap's
Q1 gate says implementation does not begin until the conditions below are explicit — so this is the
design work, not a preliminary to it.

Three of V1-6's outcomes force decisions that were deliberately deferred earlier, and they are flagged
as such rather than smuggled in as implementation details.

## What the text surfaces actually look like today

Measured, not assumed.

| Fact | Evidence |
|---|---|

## Decisions

### D-A — **Forced:** does the application chrome adopt the installed face?

This is the font plan's deferred D-D, and V1-6 cannot proceed without settling it: outcome 1 makes
authored UI content UTF-8, and the chrome currently declares the built-in ASCII face *permanently*. A
Japanese menu label would therefore render as a solid field of sentinels — the phase would ship a
correctness feature that looks like a bug.

| Option | Consequence |
|---|---|
| Chrome stays ASCII forever | Authored UI must stay ASCII, which contradicts outcome 1 outright. Rejected |
| **Chrome adopts the installed set when that set covers printable ASCII; otherwise stays built-in** | **Recommended.** Menus keep rendering even with a CJK-only face, and gain the user's face when it can serve them |
| Chrome adopts whatever is installed | A CJK-only set turns the menus into magenta-on-red marks — the failure D-D existed to prevent |

**The test is the set, not the manifest prose.** "Covers printable ASCII" should be computed by asking
the set whether it contains U+0020–U+007E — a property the bytes already answer — rather than trusting a
`coverage=` line somebody typed. That keeps D12's "declare, don't assume" intent without letting a
declaration lie, and it needs no format change.

### D-B — **Forced (register B2):** does a cluster always occupy one cell?

| Option | Consequence |
|---|---|
| **One cluster = one cell, always; a full-width figure is drawn narrower by the font** | **Recommended.** 8×8 is the visual language; the raycaster's logical cells, the SMC fingerprint and every layout rule assume one cell per shape |
| Double-width cells for full-width characters | Changes `Grid`, projection, packed state and every layout rule — a representation change of the same order as V1-5, for a look that 8×8 CJK faces already deliver |

The font has already answered this: Misaki's full-width glyphs are 8×8 bitmaps. B2 decides *layout*
behaviour only, and the answer is that a cell is a cell.

### D-C — **Forced (V1-4 D5):** bidi, now or refused?

D5 deferred bidi to V1-6, "constrained: a table-driven UAX#9 subset generated at conversion time; until
then RTL is refused with a typed diagnostic".

| Option | Consequence |
|---|---|
| **Refuse RTL with a typed diagnostic; implement the UAX#9 subset as its own later increment** | **Recommended for this phase's first pass.** Honest, small, and it cannot render text backwards by accident |
| Generate and apply a UAX#9 subset now | Correct by the outcome's letter, and a substantial increment on its own: reordering, mirroring, and its interaction with wrapping |

**This is a real deviation and needs your explicit yes.** Outcome 3 names "bidi visual behavior", so
choosing refusal means V1-6 closes that outcome as *refusal + diagnostic* rather than as rendering. The
alternative is that bidi becomes the phase's largest increment and everything else waits behind it.


### D-D — Capacity: bytes or clusters?

| Option | Consequence |
|---|---|
| **Keep `content[256]` as bytes; every write truncates only at a cluster boundary** | **Recommended.** No format or struct change, no migration; the one new rule is "never split a cluster" |
| 256 *clusters* (buffer ≈ 1 KB) | Makes the limit script-independent, at the cost of a struct and format change plus a migration for every document |
| Capacity in cells | Couples the document to the display scale, which V1-5 deliberately kept independent |

The byte limit is a property of the file format; changing it is a migration with its own compatibility
questions. Truncating at a cluster boundary turns a silent corruption into a defined, testable rule.

### D-E — Paste policy: refuse, never half-apply

A paste is one transaction. Rules, in the order they are checked:

1. **Not text on the clipboard** (empty, or an unsupported type): nothing happens and no diagnostic is
   raised. That is a `STATUS`, not an error.
2. **Malformed UTF-8 anywhere**: refuse the whole paste, naming the byte offset and the failure kind.
3. **Would exceed the field's capacity**: refuse the whole paste. Truncating a paste is silent data
   loss, and the user cannot see what was dropped.
4. **Control characters**: refused by default — a single-line label has no business containing a
   newline — with a per-field policy where a field is legitimately multi-line.

### D-F — IME through SDL's text-input path

`SDL_StartTextInput` / `SDL_StopTextInput`, `SDL_EVENT_TEXT_EDITING` for the pre-edit string and
`SDL_EVENT_TEXT_INPUT` for commit. One code path for both required platforms; the candidate window stays
the platform's, which is what "native candidate placement where the platform permits" asks for. No
custom candidate UI attempt in v1.

### D-G — One owner for cluster-aware editing

A new pure module `src/text_edit.*` owns cursor movement by cluster, selection, Backspace, capacity and
truncation, over `text_utf8`'s primitives. Both text owners — the authored `UiDocument` and the
editor-owned fields — call it, and neither reimplements a boundary rule. No I/O, no SDL, no platform
calls, which is what makes the exit gate's "headless multilingual layout/edit tests" possible at all.


## Increments

Each is independently revertible, and ASCII behaviour must be pixel-identical after every one.

### I0 — Teach `grid_print` to read UTF-8

**Purpose.** The single text-to-cells function emits one glyph per byte today, so `あ` draws as three
wrong glyphs. Until this lands, nothing else in V1-6 is visible.

**Touches.** `src/grid.c` only: decode with `text_utf8_next_cluster`, write one cell per **cluster**,
advance one column. `grid.h` gains nothing — the signature does not change.

**Acceptance.** **Byte-identical output for ASCII** (the recorded workbench frame checksums must still
match, which is the strongest available proof the ASCII path is untouched), and a Japanese string
produces *N* cells where it used to produce 3*N*.

### I1 — `text_edit`: cluster-aware cursor, selection, capacity

**Purpose.** Outcome 3's editing half, and the shared seam D-G names.

**Touches.** New `src/text_edit.c/.h` and `tests/test_text_edit.c`; no callers yet.

**Contract.** Move left/right by cluster; Backspace deletes one cluster; truncation never splits a
cluster; capacity in bytes, with a refused-or-truncated outcome that says which happened.

**Acceptance.** Combining marks, flags and ZWJ families move as one unit; truncation exactly at a
boundary and at boundary−1 both behave; ASCII behaves as before.

### I2 — The chrome's face, and UI missing-glyph diagnostics

**Purpose.** D-A and outcome 6. Without this, I3 makes menu labels render as sentinels.

**Touches.** `glyph_source` gains a predicate ("does this set cover printable ASCII?"); the renderer's
`ui_source` is chosen at load time by that predicate; the missing-glyph report covers the UI surface too.

**Acceptance.** No set: chrome unchanged. Full-ASCII set: the chrome uses it. CJK-only set: the chrome
stays built-in and the menus stay readable. A UI codepoint above ASCII raises `TSG-ASSET-ENV-0001` with
the UI face named.

### I3 — Authored content becomes validated UTF-8

**Purpose.** Outcome 1, the phase's headline.

**Touches.** `ui_document` load/save (validate; refuse malformed naming the byte offset), the truncation
rule from D-D, and the authored-menu path if it shares the reader. Old documents must still load.

**Acceptance.** A document with a Japanese label round-trips byte-for-byte; malformed content is refused
with its offset and the document is left untouched; a document that fits today still fits.

### I4 — Editor fields use `text_edit`

**Purpose.** Outcome 2 and the rest of outcome 3: cursoring, selection, Backspace and alignment in the
editor's own fields, kept distinct from authored UI as the outcome requires.

**Acceptance.** Left/right/Backspace move by cluster; selection boundaries are cluster boundaries; a
field at capacity refuses rather than splitting.

### I5 — Clipboard paste

**Purpose.** Outcome 5, under D-E's four rules.

**Acceptance.** One test per rule: non-text clipboard is silent; malformed paste refused whole with an
offset; over-capacity paste refused whole; a control character refused. A successful paste is one undo
step.

### I6 — IME

**Purpose.** Outcome 4.

**Acceptance.** Pre-edit visible and distinguishable from committed text; commit replaces pre-edit
atomically; cancel discards it; moving focus mid-composition does not leave pre-edit behind.

## Exit gate and what cannot be verified here

Outcome 3's bidi clause is the open question (D-C). Everything else is testable headlessly except the
native acceptance the roadmap names — Linux and Windows keyboard, clipboard and representative CJK IME —
which needs hardware this environment does not have and will be recorded as unrun rather than assumed.

**What must not change:** the cell model (one codepoint, 10 bytes, 64-bit state), `UiDocument` IDs,
hierarchy, history and runtime separation, and the validity of ASCII documents.

## Sign-off

Approving this plan approves **D-A** (chrome adopts the installed face when it covers printable ASCII),
**D-B** (one cluster, one cell), **D-D** (byte capacity, truncate at cluster boundaries), **D-E** (paste
refuses rather than half-applies), **D-F** (SDL text-input path, platform candidate window) and **D-G**
(one editing owner). **D-C is the one that needs a decision rather than an ack**: refusal now with bidi
as its own later increment, or bidi inside V1-6 and everything else queued behind it.


## Progress

### I0 — `grid_print` reads UTF-8 — **landed 2026-11-25**

**Decision recorded:** D-C taken as recommended — **RTL is refused with a typed diagnostic**, and the
UAX#9 subset is its own later increment. That is a deviation from outcome 3's wording and is written
here so it cannot be mistaken for a completed bidi implementation.

**What changed.** `grid_print` now walks grapheme clusters through `text_utf8_next_cluster` and writes
one cell per cluster, taking the cluster's first codepoint. `\n` still breaks the line. Byte-for-byte,
ASCII is untouched.

**Three deviations from this plan, each for a reason:**

1. **The signature returns `bool`, it does not stay `void`.** The plan said "`grid.h` gains nothing —
   the signature does not change". That was wrong: a 4-byte sequence is a codepoint above U+FFFF, which
   the 16-bit cell cannot address, and a `void` function would have to either truncate `U+1F600` to
   `U+F600` — drawing a different character and calling it success — or silently stop. Returning `bool`
   is the smallest honest fix, and all 90 existing call sites compile unchanged.
2. **The Makefile is part of the change.** `SRC_GRID` now carries `src/text_utf8.c` and the vendored
   `utf8proc.c`; `INCLUDES` gained the vendored include directory; the application rule gained
   `$(UTF8PROC_SRC)` because `SRC_FILES` is a `wildcard src/*.c` that picks up new modules but knows
   nothing about `vendor/`; and one rule that spelled `src/grid.c` literally now says `$(SRC_GRID)`.
   That last one is the `b632998` lesson, met again and fixed the same way.
3. **A pre-existing test asserted the behaviour this increment removes.**
   `test_grid_print_treats_high_bytes_as_latin1` in `test_core` pinned "a lone 0xE9 becomes U+00E9".
   Its intent was **updated, not deleted**: a lone `0xE9` is a malformed UTF-8 lead, so it is now
   refused — while keeping the half that still matters, that a high byte must never arrive
   sign-extended as `U+FFE9`.

**Two findings worth carrying forward:**

- **Astral characters cannot be drawn at all.** Emoji and anything above U+FFFF are now *refused*
  rather than truncated, which is consistent with V1-5's 16-bit cell and with the deferred
  "full/color emoji" in the product model — but it means the refusal is the user-visible behaviour, and
  a caller that ignores the return value will simply see a short line.
- **A cluster is atomic.** A malformed byte discovered while reading a cluster discards that cluster
  too, so `"A\x80"` writes nothing. Committing half a cluster was judged worse than committing none;
  the test states the trade-off rather than hiding it.

**Verification.** `test-grid-print` **9/9** (ASCII unchanged; newline; 2-byte and 3-byte one cell each;
a combining mark costs no column; astral refused with nothing written; malformed stops the walk;
over-long cluster stops the walk; nulls refused). `make test` **94 runners / 1033 tests, 0 failures**.
`make check-ui-workbench-frame` → **recorded checksums match**, which is the strongest available proof
that the ASCII path is byte-identical. `standards-core` 6/6. Smoke `{"smoke":"ok",…}`.


### I1 — `text_edit`: cluster-aware cursor, deletion and capacity — **landed 2026-11-25**

**What changed.** New pure module `src/text_edit.c/.h`: boundary queries, previous/next boundary,
cluster Backspace, and a capacity copy that truncates only at a boundary. No I/O, no SDL, no globals.
**No callers yet**, which is the plan's intent — the seam is settled and tested before an editor field
is allowed to move a cursor by byte.

**One API decision the plan did not foresee.** `text_edit_next_boundary` requires its offset to be a
boundary and returns `TEXT_EDIT_INVALID_ARGUMENT` otherwise, while `text_edit_prev_boundary`
deliberately *snaps back* to the boundary before a non-boundary offset. The asymmetry is intentional:
forward from inside a cluster would decode a continuation byte and report a boundary that is not one,
whereas "move left" from a stale cursor should do the forgiving thing. Both halves are tested.

**Other contract points worth naming.** A cursor at 0 is `TEXT_EDIT_OK` with nothing deleted — not an
error, just nothing before it. A cursor *inside* a cluster is `TEXT_EDIT_MALFORMED`, because deleting a
guess is worse than refusing. `text_edit_fit` validates the whole source before copying, so a malformed
tail cannot leave half a field behind; and it distinguishes `TEXT_EDIT_TRUNCATED` from
`TEXT_EDIT_NOTHING_FITS`, which is what lets the paste path (D-E) treat anything other than
`TEXT_EDIT_OK` as "refuse the paste".

**An asymmetry worth recording before it confuses someone.** A regional-indicator flag and a ZWJ family
each move as **one** step here, even though `grid_print` refuses to *draw* them — they are above
U+FFFF, which a 16-bit cell cannot address. Editing a character and being unable to draw it is
uncomfortable but correct for now: editing is text, drawing is cells, and V1-5 decided the cell's width.
It is also the shape the "full/color emoji are deferred" line in the product model implies.

**Verification.** `test-text-edit` **11/11**: ASCII boundaries; a combining sequence as one step; the
forward-from-inside refusal and the backward snap; flag and ZWJ family as single steps; Backspace
deleting a whole cluster and landing the cursor at its start; Backspace at 0 unchanged; Backspace
refusing an inside-a-cluster cursor; truncation at an exact boundary *and* at boundary−1; nothing-fits;
malformed refused with the destination untouched; argument and empty-input cases. `make test`
**95 runners / 1044 tests, 0 failures**. `make check-ui-workbench-frame` → checksums match.
`standards-core` 6/6.

### I2 — The chrome's face, and UI missing-glyph diagnostics — **landed 2026-11-25**

**What changed.** Four pieces, each small:

1. `glyph_source_set_covers_printable_ascii` asks the **set bytes** for U+0020–U+007E — 95 lookups — rather
   than trusting a manifest's `coverage=` line. A declaration can be wrong; a lookup cannot.
2. `glyph_source_ui_face(installed)` is the whole of D-A as one expression: the installed set when it
   covers the interface, otherwise `NULL`, which already means the built-in ASCII face.
3. `renderer_set_world_glyph_set` was renamed `renderer_set_glyph_set` and now installs **both** faces,
   because there is one installed face and each surface asks whether it can use it. Nothing else writes
   `ui_source`.
4. `report_missing_glyphs` became two calls to one `report_missing_surface`, and the line now names the
   surface (`world`/`ui`) as well as the face.

**Two design decisions this increment had to make on its own:**

- **The missing-glyph state had to be split in two.** One `GlyphMissingState` is keyed to the face that
  filled it (`D-C`/I4), so a single state serving world *and* chrome would re-adopt the face on every
  surface switch and re-report the same gaps every frame — the exact storm I4 was built to prevent.
  `Renderer` now holds `missing_world` and `missing_ui`, and the compositor takes the pointer explicitly.
  That is why `ui_compositor_compose` gained a parameter: a surface that can detect a gap must be able to
  record it against its own face.
- **The policy moved out of the renderer.** `renderer_create` needs a real SDL window and no test in this
  suite builds one, so a policy living inside `renderer_set_glyph_set` would be the only untestable line
  in the phase. It is `glyph_source_ui_face` instead — pure, headless, and the renderer merely calls it.

**Acceptance, each point against evidence:**

| Required | Evidence |
|---|---|
| No set → chrome unchanged | `test-ui-compositor` 9/9 including the recorded-scale checks, `test_glyph_source` "built-in answers ASCII only when no set is declared", and the workbench frame checksums (chrome is drawn by the same compositor path) |
| Full-ASCII set → chrome uses it | `test_chrome_adopts_only_a_face_that_can_draw_the_interface`: a 95-codepoint set is adopted by pointer identity |
| CJK-only set → chrome stays readable | Same test: a one-glyph CJK set is **refused** (`NULL`), so the menus keep the built-in face |
| UI codepoint above ASCII → `TSG-ASSET-ENV-0001` naming the UI face | `test_missing_codepoint_is_noted_for_the_chrome`: U+3042 on a chrome canvas is recorded, reported once, and the *second* frame reports nothing while still counting the cell |
| One printable codepoint missing is not coverage | `test_printable_ascii_coverage_is_all_or_nothing` drops only `~` and the set is refused |

**A near-miss worth stating plainly.** A face with 94 of the 95 printable glyphs is exactly as unusable
for the interface as one with none: the missing glyph would be a sentinel in a menu. Coverage is
all-or-nothing, and the test says so by dropping the single character a careless build is most likely to
lose.

**Verification.** `test-glyph-source` **7/7**, `test-ui-compositor` **9/9**, `make test`
**95 runners / 1047 tests, 0 failures**, `make matrix` **7/7**, `standards-core` 6/6,
`make check-ui-workbench-frame` → **recorded checksums match**, `make leak` → **PASS
(memcheck-clean)**.

**End to end, on a real render loop.** With the V1-5 one-glyph fixture installed as
`assets/fonts.tsgfont` and `--benchmark-scenario ui --frames 3`:

```
glyphs: loaded 1 glyphs from assets/fonts.tsgfont
TSG-ASSET-ENV-0001: world face c0ec8660cc630f21 lacks U+0020 at cell 0,0 (41600 affected this frame)
... eight named codepoints ...
```

Three things this observation does establish: the new `world`/`ui` word prints where the old line
printed; the eight-plus-overflow bound still holds; and **not one `ui` line appeared while the world was a

that a poor-ASCII face cannot make the menus unreadable.

**What this observation does not establish, stated so it is not overclaimed.** The `ui` *sentence* has not
been seen in a real run, and cannot be: the chrome's canvases are ASCII today, so with either face its

The fixture was deleted from `assets/` immediately after the run (confirmed absent).

### I3 — Authored content becomes validated UTF-8 — **landed 2026-11-25**

**What the code turned out to be.** `UiDocument.content` was gated by one predicate: printable ASCII
U+0020–U+007E, no backslash, `length < 256`. The file format is line-oriented `key=value` with no
escaping, written with `fprintf("%s")` and read with `fgets` + `copy_string`. So the change was never about
the format — it was about the predicate, and about making its refusals *locatable*.

**What changed.** Four pieces:

1. `text_utf8` gained `text_utf8_next_codepoint` (a per-codepoint walk) and `text_utf8_classify`
   (`PLAIN` / `CONTROL` / `RIGHT_TO_LEFT`) — **from the vendored `utf8proc` data**, not a handwritten
   range table, for the same reason D10 pins the Unicode version to that data. `utf8proc` is still reached
   through exactly one module.
2. New pure `src/ui_text.*` owns "what may live in an authored field", reporting
   `{result, offset, codepoint}` — the same shape as the other typed refusals in this codebase.
3. `ui_document`'s `valid_content` delegates to it (ASCII behaviour preserved exactly), and the reader
   validates each `content=` value **where the line is still in hand**, returning
   `ui_document_load_diagnosed` with `line`, `column`, `codepoint` and the reason.
4. `write_document` was not touched: it already wrote UTF-8 bytes faithfully with `%s`.

**Four rules, and why each is a decision:**

| Rule | Reason |
|---|---|
| Strict UTF-8, offset named | Overlong forms, surrogates and >U+10FFFF are refused rather than silently repaired |
| No Cc or Cf | Invisible characters have no place in a single-line label; this covers NUL, DEL, C1 and the bidi embeddings/overrides/isolates **without a second concept for them** |
| ZWJ and ZWNJ exempt | They are how a cluster is spelled. Refusing them would make emoji sequences unrepresentable, so they stay `PLAIN` |
| No RTL | D-C's typed refusal. Drawing Arabic left-to-right is a silent wrongness, so the refusal lives at ingest where a position can be named |

**Three decisions this increment had to make on its own:**

- **Capacity stays a refusal, and is tested at the cluster boundary.** D-D's clause is "a *truncating*
  write cuts only at a cluster boundary"; I3 introduces no truncating write. Silently shortening a file
  that claims more than the model holds would lose text on the next save, so content refuses as it always
  has — and `text_edit_fit` stays the only sanctioned cutter for I4/I5. Recorded here because D-D's
  wording could be read as "truncate", and it is not what a document should do to someone's file.
- **The second authored door is deliberately left alone.** `ui_ele.c` parses `assets/ui_elements/*.txt` with
  its own reader. It is not the surface outcome 1 names (`UiDocument`), it has **no diagnostic channel**,
  and a refusal there would be silent — the very thing this increment exists to stop. When it gains the
  rule it should gain a channel at the same time; that belongs with I4, which touches the editor anyway.
  All 70 shipped element files are pure ASCII, so nothing is waiting on it.
- **The position is plumbed to the API, not yet to a screen.** `ui_menu_workspace` reports
  `LOAD_FAILED` as a code and has no status-message channel to carry a line and column, so the editor
  surface for the diagnostic is I4's work. What I3 guarantees is that the information exists, is exact,
  and is tested.

**Two mistakes of mine, both caught by tools rather than by thinking:**

1. My first tests set content on element id `2`. Id 2 is the *panel* (a container), so `set_content`
   correctly refused with `INVALID_CONTENT` and I spent a cycle believing the validator was broken. The
   title is id 3. The refusal was right; the test was wrong.
2. Adding `$(SRC_TEXT_UTF8)` to every rule that mentions `$(SRC_UI_DOCUMENT)` duplicated `utf8proc` in
   `test-flow-project-catalog`, because that rule also expands `$(TEST_SCENE_DOCUMENT_SRC)`, which contains
   `$(SRC_GRID)` — and `SRC_GRID` now carries `$(SRC_TEXT_UTF8)`. My paragraph scan could not see a
   dependency that arrives through a variable. `b632998`'s lesson has a corollary: grep the variables, not
   just the rule.

**Acceptance, each point against evidence:**

| Required | Evidence |
|---|---|
| A document with a Japanese label round-trips byte-for-byte | `test_utf8_content_round_trips_byte_for_byte`: `content=HP ああ` appears in the file, loads back equal, and a second save writes **byte-identical** bytes |
| Malformed content is refused with its offset | `test_malformed_content_is_refused_with_its_position`: `A\x80 B` → `INVALID_CONTENT`/`MALFORMED`, `line` computed from the file by the test rather than assumed from the writer, `column == 9` ("content=" is 8 bytes, then `A`) |

**A consequence worth stating before someone ships the first Japanese label.** Validating and storing

Japanese into any `assets/menus/*.tui` here: doing so without the face would trade a working ASCII menu for
a diagnostic field, which is precisely the failure D-A exists to prevent.

### I4 — Editor fields use `text_edit` — **landed 2026-11-25**

**What was actually there.** The editor's text fields were **append-only**: `edit_text` + `edit_text_length`,
drawn as `"%.120s_"`, with Backspace deleting the last *byte* and Left/Right meaning "decrease/increase the
selected value" rather than "move a caret". There was no caret and no selection anywhere in the field
model, so outcome 3's "cursoring … selection" had nothing to be cluster-safe *about*.

**What changed.**

1. `text_edit` gained the primitive the field needed and Backspace alone cannot express:
   `text_edit_replace_range` (insert at a caret, delete a range, replace a range — one function), plus
   `text_edit_selection` to order an anchor/caret pair. Both refuse a range that is not cluster-aligned and
   validate the replacement before touching a byte.
2. `UiMenuWorkspace` carries `edit_text_cursor` / `edit_text_anchor` (and the same pair for the
   create-name field). Typing inserts **at the caret**, replacing any selection; Backspace deletes the
   selection if there is one and otherwise one cluster; arrow keys move by cluster; Shift extends.
3. `INPUT_KEY_LEFT/RIGHT` with Shift now set `editor_caret_extend_pressed`, and the editor host maps
   Left/Right to the new `CARET_LEFT`/`CARET_RIGHT` actions **in text modes only** — everywhere else those
   keys still decrease and increase values. Additions are `SELECT_ALL` (the one selection arrows cannot
   reach) and `_REJECTED_TEXT` / `_FIELD_FULL` result codes so a refusal is visible to the caller instead
   of silent.
4. The panel draws the caret at its own offset and a selection between `[` and `]`. With the caret at the
   end — where every field opens — the line is byte-for-byte the `text_` the editor always drew.

**Three decisions worth recording:**

- **Content is refused whole; an identifier filters.** Content is `ui_text`'s rule (I3), so a keystroke that
  introduces a control character is refused and nothing changes. An identifier (`[A-Za-z0-9_-]`) keeps the
  long-standing behaviour of filtering to the characters it can use — `"play now!"` still becomes
  `"playnow"`, and a multi-byte character is now dropped **as one codepoint** rather than as three
  unusable bytes.
- **Capacity refuses; it never truncates.** `text_edit_replace_range` returns `NO_ROOM` and the field
  returns `FIELD_FULL` with the buffer untouched, so two bytes cannot sneak in where one does not fit.
  This is the reading of D-D that the I3 record already argued for; D-E's "refuse the whole paste" is the
  same rule arriving from the other direction.
- **A plain arrow collapses a selection to the edge it is heading for** instead of stepping one cluster
  from an end the user can no longer see. That is what every editor does and what makes Shift+arrow
  reversible.

**A bug this increment found in the primitive it depends on.** `text_edit_backspace` adjusted `*size` but
never moved the NUL, so a field whose length said 6 while its terminator sat at 7 read back as seven bytes
to every `strlen`. I1's tests were size-based and could not see it; the editor's fields are C strings and
caught it immediately (the create-name test failed on the trailing character). Fixed in `text_edit.c` with
`if (*size < capacity) bytes[*size] = '\0';` so no future field owner has to remember.

**Two mistakes of mine in this increment, both mine and both caught by tests:**

1. My first test string arithmetic was wrong: `"a" + あ + "e" + combining` is **7** bytes with boundaries
   at 0, 1, 4, 7 — I wrote 6 and had to correct four expectations.
2. My host test cleared `editor_decrease_pressed` to simulate Shift+Left. Shift arrives **alongside** the
   arrow, not instead of it, so the action became `NO_ACTION`; the test now models what `input.c` really
   produces.

**Acceptance, each point against evidence:**

| Required | Evidence |
|---|---|
| Left/right move by cluster | `test_caret_moves_by_cluster_not_by_byte`: from the end of `a あ e ́`, Left lands on 4, 1, 0 and stops; Right on 1, 4, 7 and stops |
| Selection boundaries are cluster boundaries | `test_selection_extends_with_shift_and_collapses_without`: anchor 7, caret 4 → 1 → 0, then a plain arrow collapses to 7; `text_edit_selection` orders in both directions |
| Backspace deletes one cluster | `test_backspace_deletes_a_selection_or_one_cluster`: `"a あ"` → `"a"` with all three bytes gone; selection deletes exactly itself |
| A field at capacity refuses rather than splitting | `test_field_at_capacity_refuses_without_splitting`: 255 bytes + `"y"` → `FIELD_FULL`, state unchanged; a two-byte character is refused where one byte would fit |
| Typing lands at the caret | `test_typing_inserts_at_the_caret_and_replaces_a_selection`: `"abc"` caret 1 + `"Z"` → `"aZbc"`, cursor 2; selecting all and typing あ replaces the field |
| Keys mean what they mean | `test_text_mode_arrows_move_the_caret`: in a text mode Left moves the caret and leaves the text; the same flag still decreases a value outside one |

**Verification.** `test-ui-menu-workspace` **24/24** (the six new ones plus the eighteen that already
exercised the menu flow, unchanged), `test-text-edit` **14/14**, `test-ui-editor-host` **5/5**,
`test-ui-editor-presentation` **4/4**. `make test` **96 runners / 1073 tests, 0 failures**; `make matrix` **7/7**;
`make check-ui-workbench-frame` → **checksums match** (the editor's frame is byte-identical with
the caret at the end, which is where every field opens); `standards-core` 6/6; `make style`
(cppcheck) **PASS**; `make leak` **PASS (memcheck-clean)**.

**Still open, and deliberately not in this increment.** The `ui_menu_workspace_append_text` path now
refuses what the document would refuse, but the *presentation* has no place to show why: `REJECTED_TEXT`
and `FIELD_FULL` are returned to the host and dropped. A status line needs the same channel that I3's load
diagnostic is waiting for, and both belong together — that is the next increment's first task, not a

### I5 — Clipboard paste under D-E — **landed 2026-11-25**

**What was there.** Nothing: `grep -i clipboard src/` returned not one hit. There was no clipboard reader,
no paste key and no paste policy.

**What changed.**

1. `src/platform_clipboard.*` reads the system clipboard through SDL and **never truncates**. Its four
   results are the four answers a caller needs: `OK`, `EMPTY` (a status), `TOO_LARGE` (a refusal, because
   rule 3 says so) and `UNAVAILABLE` (no video subsystem, or SDL refused). The decision half lives behind
   `platform_clipboard_internal_read_text`, the same seam style as the other `platform_*` modules, so it is
   testable without a desktop.
2. `ui_menu_workspace_paste_text` applies D-E in order: nothing → silent `NO_ACTION`; **capacity before
   encoding** (capacity is arithmetic and needs no interpretation, and "too large" is the more useful
   answer for a paste that is also malformed); malformed → `REJECTED_TEXT` with the byte offset; a
   character the field forbids → `REJECTED_TEXT` with its own reason. Every refusal leaves the field
   byte-for-byte unchanged, so it can be retried.
3. Ctrl+V is an input flag; the host turns it into `UI_EDITOR_ACTION_PASTE` **but takes the clipboard text
   as a parameter**, because the host has no platform calls and that is what keeps it testable on both
   platforms. Both production hosts (`ui_editor_runtime`, `unified_editor`) read the clipboard only on the
   frame the key is pressed and only when a field is open, so there is no per-frame allocation and no
   clipboard traffic from modes that cannot use it.

**Decisions this increment had to make:**

- **Paste refuses whole; typing filters.** `append_text` on an identifier keeps the legal characters
  (`"play now!"` → `"playnow"`), which is long-standing behaviour and friendly while typing. A *paste* of
  the same string is refused, because dropping half of what someone pasted is exactly the half-application
  D-E forbids. `identifier_accepts` therefore checks instead of filtering, and the test says so.
- **Capacity is checked before encoding.** Both are refusals, so the order only changes which reason is
  reported — and "it does not fit" is the one a user can act on without editing the source text.
- **"One undo step" is a property of the edit, not of a special path.** A paste is one
  `text_edit_replace_range` call, so committing it records one change; `test_a_paste_is_one_undo_step`
  proves that one undo returns to the pre-paste document, and that the field edit is not itself a change.

**Three mistakes of mine here, all caught by tools:**

1. `paste_text` called `text_mode_accepts`, which I had deleted in I4 — the compiler found it, and the fix
   added `identifier_accepts` rather than resurrecting a filter into a paste path.
2. My first platform test copied `"keep"` into a `char[4]` (`sizeof` includes the terminator) — the
   fortified `memcpy` caught it.
3. Two expectations were simply wrong about my own contract: five bytes of text **do** fit a six-byte
   buffer, and the reader clears the buffer on entry, so a refusal leaves an empty buffer rather than the
   previous contents. I kept the clearing (a stale buffer looking current is the worse trap) and documented
   it, which is the opposite of what the first test asserted.

**Acceptance, one test per rule:**

| D-E rule | Evidence |
|---|---|
| 1. Not text on the clipboard: nothing happens, no diagnostic | `test_paste_of_nothing_is_silent`: empty and `NULL` are `NO_ACTION` with the field untouched and the diagnostic cleared; `test_empty_clipboard_is_a_status` for the platform half |
| 2. Malformed anywhere: refuse whole, name the offset and kind | `test_paste_of_malformed_text_is_refused_with_its_offset`: `"ok\x80ok"` → `REJECTED_TEXT`/`MALFORMED` at byte 2, field unchanged, and a valid paste into the same field still works |
| 3. Would exceed capacity: refuse whole | `test_paste_that_does_not_fit_is_refused_whole`: 271 bytes into 256 → `FIELD_FULL`, unchanged; the same paste fits once a selection is removed, because the check subtracts what it replaces; `test_too_large_is_refused_and_writes_nothing` for the platform half |
| 4. Control characters refused | `test_paste_with_a_control_character_is_refused`: newline at byte 4, tab, and an RTL letter refused with `RIGHT_TO_LEFT`; all leave the field untouched |
| A successful paste is one undo step | `test_a_paste_is_one_undo_step`: paste + commit → `change_count + 1`, one undo restores `PLAY` |

### I6 — IME through SDL's text-input path — **landed 2026-11-25**

**What was there.** `SDL_StartTextInput` was already managed for the editor's fields, and committed text
already arrived as `SDL_EVENT_TEXT_INPUT`. Nothing handled `SDL_EVENT_TEXT_EDITING`, so a composition was
invisible: the user typing Japanese saw nothing until they committed, which is the one IME behaviour nobody
can work with.

**What changed.**

1. `input` gained `INPUT_EVENT_TEXT_EDITING` and an `InputState` composition block (`text_editing`,
   `_len`, `_cursor`, `_selection`, `_active`). It is deliberately **not** cleared per frame — SDL re-sends a
   composition only when it changes and sends an empty one when it ends, so clearing between frames would
   blink the composition off and on — and `input_begin_frame` leaves it alone, which is tested.
2. `UiMenuWorkspace` holds `edit_preedit` next to the field. It is shown after the caret, is **never part of
   the text**, and is cleared by: the commit that replaces it, Backspace, paste, a caret move, opening a
   field, Esc, and Enter. Zeroed rather than merely terminated, so "nothing of it is kept" is true byte for
   byte.
3. The host maps an active composition to `set_preedit` and **committed text wins** when a frame carries
   both. That ordering is not cosmetic: SDL sends the editing event first and the commit second, so
   preferring the composition would drop the very character the user just chose.
4. The panel draws the composition in braces after the field — `PLAY Now{にほん}` — so committed text and
   text still being chosen cannot be confused.

**Decisions this increment had to make:**

- **A pre-edit is not held to the authored-text rules until it is committed.** A composition legitimately
   passes through states no field would accept (a bare consonant while romaji converts), so the pre-edit is
   only required to be well-formed UTF-8 — enough to draw — while `ui_text` decides the commit. That way the
   refusal for a bad commit names the byte, as it does for typing and pasting.
- **A composition that does not fit is truncated at a cluster boundary** (`text_edit_fit`) rather than
   refused: refusing to *show* it would leave the user typing blind, and nothing is stored by showing it.
- **Any field mutation or caret move ends the composition.** It is anchored where the caret was; leaving it
   up after the anchor moved would show it pointing at a spot the text no longer occupies.

**Mistakes of mine, and what caught them:**

1. I wrote the host comment for the *wrong* order — claiming the composition should be checked before the
   commit — and the edit asserted against the file instead of applying, which is how I noticed. Thinking it
   through (SDL sends editing-then-commit) gave the right order and a test for it.
2. Two insertions landed **inside** a function body again (the same trap as I4/I5), producing nested
   functions; the compiler refused, and both were moved by hand.
3. My first "cancel leaves no trace" assertion compared the whole struct, which cannot pass while the
   pre-edit's own bytes linger — and cmocka cannot say which byte differed. I made the clearing zero the
   buffer and stated the property over the fields a caller can observe.
4. A `snprintf` of field + composition was rejected by `-Werror=format-truncation`; fixed shares of the
   line buffer replaced the guess, and a leftover dead `field_used` computation was removed rather than
   left in.

**Acceptance:**

| Required | Evidence |
|---|---|
| Pre-edit visible and distinguishable from committed text | `test_preedit_is_shown_but_never_committed`: the composition appears in `edit_preedit`, the field still says `ab`; the panel draws it in braces (presentation change, exercised by the existing frame tests) |
| Commit replaces pre-edit atomically | `test_composition_is_shown_and_the_commit_wins`: a frame with both puts `に` in the field and leaves no pre-edit; `test_preedit_is_shown_but_never_committed` for the workspace half |
| Cancel discards it | Empty composition, and Esc, both leave `has_preedit == false` with the field untouched |
| Moving focus mid-composition leaves no pre-edit | `test_leaving_the_field_discards_the_composition`: Esc, a caret move, and a non-text mode |

**Verification.** `test-input` **18/18** (the composition survives `input_begin_frame`, ends on an empty
editing event, and is filtered in headless mode), `test-ui-menu-workspace` **33/33**,
`test-ui-editor-host` **6/6**. `make test` **97 runners / 1088 tests, 0 failures**;
`make check-ui-workbench-frame` → **checksums match**; `standards-core` 6/6; `make all` clean under
`-Werror`.

**Cannot be verified here.** A real IME: this host has no input method installed, so the ASCII acceptance

### I7 — Visible refusals (the status line I3–I5 kept deferring) — **landed 2026-11-25**

**Why this exists.** Three increments ended with the same sentence: the refusal is typed, exact and tested,
and the surface has nowhere to show it. `REJECTED_TEXT`, `FIELD_FULL` and the load's line/column were
returned to the host and dropped. A refusal a person cannot see is a keystroke that silently does nothing,
which is the failure mode this phase was supposed to remove.

**What changed.**

1. The workspace keeps the reason, not just the code: `last_text_diagnostic` / `last_text_refused` and
   `last_load_diagnostic`, filled by `append_text`, `paste_text` and the load path, cleared by the next
   operation that succeeds. `ui_menu_workspace_last_text_diagnostic` returns NULL when there is no
   character to blame (a full field), which is itself information the surface uses.
2. The presentation builds the line: `Text refused: CONTROL at byte 1 (U+000A)`, `Field full: nothing was
   added`, and `Load failed: line 12 col 9: MALFORMED` — reusing `ui_text_describe`, so the wording of a
   refusal exists in exactly one place.
3. **The note is now passed to the panel in text modes.** It was drawn for the chooser and the property
   lists and passed as `NULL` for the fields — which is why the first version of the test failed: the
   message existed and had nowhere to go. That was the real defect, not the test.

**What it cost, and what it caught.** Recording a reason means the *workspace* is no longer byte-identical
after a refusal, so nine assertions of the form `assert_memory_equal(&workspace, &before, …)` started
failing. They were over-asserting: the claim D-E and I4 make is about the *field* (and, for a load, the
*document*). They now say exactly that, through `assert_field_unchanged`, and the load test additionally
asserts that a structural failure records **no** position while a content failure does.

**Acceptance.**

| Required | Evidence |
|---|---|
| A refused keystroke is visible, with reason and position | `test_refusal_reason_is_drawn`: the grid contains `Text refused: CONTROL at byte 1` |
| The reason is the right one, and stale reasons do not linger | `test_text_refusals_record_their_reason`: CONTROL at 1 for a newline, MALFORMED at 2 for a paste, NULL after a success, NULL for a full field |
| A refused load says where | `test_refused_load_records_its_position`: one corrupted byte in a saved document → `MALFORMED` at column 10 of its line; the structural case records nothing |
| The field (and document) are still untouched by a refusal | `assert_field_unchanged` across the nine text tests; `document`/`has_document`/`mode` for the load |

`make check-ui-workbench-frame` → **checksums match** (the editor's panel is not in the recorded frames, but
checking it is cheaper than assuming); `standards-core` 6/6; `make style` (cppcheck) **PASS**;
`make leak` **PASS (memcheck-clean)**.
